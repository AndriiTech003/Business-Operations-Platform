## Gap fixes (2026-10-05)

Closed after the first build, each with automated tests (file names in parentheses).

1. **PATCH touches only the fields that were sent.** zod 4 applies `.default()` inside `.partial()`, so `PATCH /v1/contacts/:id` reset `lastName` to `''`, and the same bug hit every PATCH built from a create schema: deals (`amountCents` → 0, `currency` → USD), invoices (`currency` → USD and `lines` → `[]`, which also made a notes-only PATCH of a sent invoice fail as "locked"), tasks (`priority` → 2), custom fields (`required`/`indexed` → false, which dropped the expression index on a label change) and node retry overrides (unset keys overrode the node type's defaults). `patchSchema()` in `@bop/contracts` strips defaults before making fields optional and is used for all of them. The other PATCH/PUT endpoints (workflows, settings, members, draft, pipelines, secrets, templates) had no defaults and were checked by test. Moving a lost deal to the lost stage it is already in now updates `lostReason`. Malformed ids in paths are `400 invalid_id` instead of 500. (`contracts.test.ts`, `api.test.ts` "PATCH changes only the fields that were sent (every PATCH endpoint)", smoke)
2. **Timestamps are correct regardless of the Postgres server time zone.** `@prisma/adapter-pg` sends `Date` parameters as UTC wall time without an offset; with the server in Europe/Kiev every Prisma write landed 3 h off for raw SQL (`now()`, the `record_condition` scanner, reports). Every Prisma connection now starts with `options=-c TimeZone=UTC` (`utcConnectionString`, which also replaces any other `TimeZone` option); all columns already were `timestamptz`. Existing rows written before the fix in a dev database keep the old offset; `seed --reset` recreates them. (`timezone.test.ts`: database default time zone set to Asia/Kathmandu (+05:45), raw-SQL and `now()` comparisons, DB defaults read through Prisma, and a control showing the unfixed adapter shifts by exactly the zone offset)
3. **Untrusted markers everywhere outsiders write.** Companies have a `source` column (seed: one web-form company); a company is external when its source is `web_form`/`webhook`/`inbound_email` or it is tagged `web-form`. DTOs carry `untrusted` paths: contacts (`firstName`, `lastName`, `name`, `title`, `custom`), companies (`name`, `industry`, `custom`), nested contact/company references in deals, invoices and contacts (`name`), task `related.title`, external activities (`data.body`/`subject`/`from`), the timeline change history of external contacts/companies (`data.changes`, `data.name`, `data.merged`), and search hits (`title` + `subtitle` for external records, `subtitle` for every company/contact/invoice hit; `search_documents.external`). `ops-mcp` walks every result with `untrustedPaths()` from `@bop/contracts`, so the list is complete for all 16 tools (agent-created invoice notes are still added explicitly). (`ops-mcp` unit + integration "marks company names, nested web-form contacts, search hits and their change history")
4. **Cursor pagination in `ops-mcp`.** `list_contacts`, `list_deals` and `list_invoices` accept `cursor` and return the API's `nextCursor` (the REST API already had keyset pagination). (`mcp.test.ts` pages through every record with limit 7 and compares with a single page of 100: no gaps, no duplicates; smoke)
5. **Deterministic search order.** Ranked by `round(score, 3) DESC, title COLLATE "C", entity_id` inside each type and across types. (`mcp.test.ts` six companies with identical names)
6. **One effect ledger.** API writes with `Idempotency-Key` are recorded in `effect_log` (`origin = 'api'`, `effect` = operation scope, `request_hash`, `result.ref`) together with the replay cache in one transaction; engine rows have `origin = 'engine'`; primary key `(tenant_id, origin, idempotency_key)`. Reusing a key for a different operation is `422 idempotency_mismatch`; `POST /v1/invoices/:id/void` now honours `Idempotency-Key` too. Contract in [ADR 0012](adr/0012-one-effect-ledger-for-engine-and-api.md). (`api.test.ts`, `mcp.test.ts`, `operator.test.ts`, `tenancy.test.ts`)
7. **Run-creation rate limit and fair step scheduling.** Per-tenant token bucket in Redis (`TENANT_RUN_RATE` 50/s, `TENANT_RUN_BURST` 500; per-tenant `runsPerSecond`/`runBurst` in tenant settings, `0` = unlimited; not editable through `PATCH /v1/settings`). Manual and webhook runs are paced: the request waits for its reserved slot up to `TENANT_RUN_MAX_WAIT_MS` (2 s) and gets `429 run_rate_limited` with `Retry-After` and `retryAfterMs` beyond that; the limiter runs before any database work. Triggered runs (record events, schedules, condition scans) are never dropped: beyond the bucket their first steps get a `scheduled_for` at the reserved slot. When the tenant semaphore is full, a step is **parked** in a per-tenant Redis sorted set instead of being re-queued; every release atomically pops as many parked steps as there are free slots and nudges them, `renudgeLost` skips parked steps and the scheduler's `unparkStalled` sweep wakes them if a holder died. Job priority counts queued plus parked steps. Authentication lookups (membership, API token) are cached for 5 s per process (cleared on role change, member removal and token revocation in that process). (`fairness.test.ts`, `api.test.ts` 429 + `Retry-After`, `chaos.test.ts` mandatory #8)
8. **UI.** Dark-mode toggle in the top bar (persisted in `localStorage` `bop.theme`, applied before first paint by an inline script, system preference as default; charts and node-category colours have dark variants). Kanban keyboard moves go by stage order with a custom dnd-kit coordinate getter and instant scrolling, so Space → → → → Space reaches columns that are scrolled out of view, including the lost-reason dialog. Playwright covers dark mode, keyboard moves to the off-screen Won and Lost columns, Retry failed step and Cancel run on the run replay page, and the operator slot. (`e2e/ui.e2e.ts`, `apps/web/test/theme-operator.test.tsx`)
9. **Integration hooks for project 06.** `ai_step` calls `OPERATOR_URL` when it is set (`AI_PROVIDER` defaults to `operator` then; `fake` otherwise; `anthropic` still selectable): `POST` JSON `{task, input, labels, context: {tenantId, workflowId, runId, nodeId}}`, headers `Idempotency-Key: <step key>` and `Authorization: Bearer $OPERATOR_TOKEN`, response `{label?, summary?, confidence?}` (labels outside the configured list become `null`); 5xx/429/network errors are retried with the same key, 4xx and malformed responses fail permanently (error edge), test runs use the fake provider and mark `dryRun`. The SPA reads `GET /v1/app-config` (public) and, when `OPERATOR_EMBED_URL` is set, loads that module script once and renders `<ask-operator record-type record-id record-label agent-url console-url>` in the header of company, contact, deal and invoice pages; with no URL (or a script that fails to load) the slot renders nothing. (`operator.test.ts` against a local HTTP server, `core.test.ts`, `api.test.ts`, `theme-operator.test.tsx`, `ui.e2e.ts` with a stub component)

Breaking changes for project 06 (Wave 2 follow-up): the `ops-mcp` tool snapshot gains `cursor` on the three list tools; results now contain `untrusted` arrays inside DTOs and more `untrusted` paths; search order is stable; replay cassettes and fixtures that embed tool results need `pnpm eval:fixtures` and `pnpm eval:record`; single-effect checks can use `effect_log` (`origin = 'api'`) instead of `idempotency_records` (still written).

## Load test and bottlenecks

Full write-up in `docs/adr/0010-fair-scheduling-and-query-budget.md`, raw JSON in `docs/benchmarks/`.

- 10,000 runs (30,000 steps), 16 concurrent steps per worker: 1 worker 69 steps/s (load avg 27–29), 2 workers 197 steps/s (22–28), 4 workers 129 steps/s (34–41). 0 failed runs, 0 retries. 4 workers are slower than 2 on this shared 8-core machine.
- **Bottleneck 1 — statements per step.** A `--cpu-prof` profile showed ~45 % of worker CPU in the Prisma client runtime. Six changes (claim and lock via `updateManyAndReturn`, `runId` passed instead of re-read, input saved with completion, run status derived from loaded rows, no DTO re-fetch in `create_task`, tenant metadata cache) took the step from **22.3 to 11.6 statements** and 1-worker throughput from **74 to 148 steps/s** on 1,000 runs. The before number was measured at a higher machine load than the after number; the cache's share was measured back to back (116 → 148 steps/s). Run creation also stopped counting all active runs per start (2 s cached count; it was O(n) per run).
- **Bottleneck 2 — noisy neighbour.** Tenant B's step latency while tenant A has ~5,000 pending steps: p95 1.7–6.4 s with FIFO scheduling and the tenant semaphore checked after the Postgres claim; 57–93 ms after (a) backlog-based job priority, (b) checking the semaphore before touching Postgres, (c) spreading re-nudges of throttled jobs by backlog / limit.
- **Bottleneck 3 — run creation and retry storms (2026-10-05).** With A creating its 5,000 runs through the API during the measurement, B's p95 was 7–40× its idle p95 (load average 9–36). Most of that was A's client retrying 429s: 16–32 k refused HTTP requests, each costing authentication (a membership query) and Nest overhead. Pacing manual/webhook creation server-side (wait for the reserved token up to 2 s, 429 only beyond), checking the limiter before any database work and caching authentication lookups removed the storm (0 refusals): `chaos.test.ts` mandatory #8 measured B p95 13 ms / 9 ms under load vs 16 ms / 16 ms idle (ratio 0.81 / 0.56, load average 4–7, A's 5,000 runs created in 90 s at the 50/s limit). `node loadtest/run.mjs --noisy-only --samples=20` (`docs/benchmarks/loadtest-gapfix-2026-10-04.json`, load average 3.7–6.8): concurrent rate-limited creation → B p95 6–10 ms vs 15–16 ms idle (ratio 0.4–0.63); the stress mode with A's limit disabled (`runsPerSecond: 0`) and 5,000 steps pre-queued → B p95 42–43 ms vs 12–18 ms idle (ratio 2.4–3.5) with or without parking — a tenant allowed to bypass the creation limit still degrades neighbours beyond 2× through its eight concurrent steps; the default limit is what keeps the ratio under 2. B's p95 under load came out *lower* than idle in every paced run; warmed-up connection pools and JIT are the likely reason (not investigated further).

## Deviations from the spec and decisions taken

1. **No git and nothing git-related** (user rule): no GitHub Actions/CI, PR comments, badges for CI/coverage, changesets, hooks or `.gitignore`. Quality gates are the package scripts listed above.
2. **Local only** (user rule): no deployment, live demo, nightly reset job on a server, video or GIFs (the "Claude Desktop in 1 minute" section has the config snippet but no GIF), no publishing to npm (`@ashamrai/expr` verified with `pnpm pack`, publint, attw, size-limit). `/docs` is a self-contained page that renders `/openapi.json` instead of Swagger UI from a CDN. The real `AnthropicAiProvider` (official SDK, model `claude-opus-5-5`, low effort, server-side refusal fallbacks) is implemented and selectable with `AI_PROVIDER=anthropic` but was never called; tests, seed and smoke use the deterministic fake provider.
3. **Docker is not installed**: `docker-compose.yml` and Dockerfiles for api, worker (with Chromium), scheduler, realtime (builds project 03 next to this repo), ops-mcp and web (nginx) are written but were not built. The same processes were verified with `node dist/...` in smoke and e2e. **Testcontainers**: `TESTCONTAINERS=1` switches `createTestResources` to Postgres/Redis containers; not executed here.
4. **PostgreSQL 16** locally (devinfra) instead of 17; compose uses 17. No 17-specific features are used.
5. **Versions**: NestJS 11 (12 is ESM-only with new peers), TypeScript 6.0.3 (typescript-eslint and tsup need ≤ 6), Prisma 7.10 (8 is a release candidate), BullMQ 5.81, TanStack Table v8, Vitest 5, Playwright 1.63, zod 4. NestJS runs without emitted decorator metadata (explicit `@Inject`), see ADR 0011.
6. **Package layout**: the domain, Prisma and the engine live in `packages/core`, shared by api, worker, scheduler, seed, load test and tests (the spec lists only `contracts`, `expr`, `workflow-core`, `ui`). `apps/realtime` was added as the host for project 03's server with a tenant ACL.
7. **Raw SQL is allowed in five repositories, not only reports**: reports, search (FTS + trigram cannot be expressed in Prisma), the `record_condition` scanner (compiled expression SQL), custom-field sort and custom-field expression-index DDL. All live in `packages/core/src/raw/`, take `tenantId` explicitly and have tenant-filter tests; the lint rule forbids raw SQL everywhere else.
8. **Extra node type `create_invoice`**: template 4 ("Deal won → onboarding tasks + draft invoice") needs it; the spec's node list has no invoice action.
9. **Templates**: the overdue condition is `invoice.status in ['sent', 'partially_paid', 'overdue'] and invoice.dueDate < now() - days(1)` because the scheduler also marks invoices `overdue` (the literal spec condition would stop matching once that happens). Round-robin assignment (template 2) uses `run.number`, a per-workflow run counter that is only incremented when a definition references it. The weekly digest (template 6) calls the platform's own API through `http_request` with secrets, since no node reads report data directly; the Slack post (template 5) targets a secret URL (seeded to the local `/dev/echo` endpoint).
10. **Runs work on a snapshot of the trigger record** (ADR 0008).
11. **Test runs**: waits resolve immediately (`wait_for_event` takes `timeout`), approvals are auto-decided (`approve`/`reject` option), emails/HTTP/record updates/tasks/notes only produce previews; test runs do not write the outbox or audit log.
12. **Noisy neighbour criterion**: the test asserts the spec's ≤ 2× on p95 without a floor. Tenant A creates its 5,000 runs through the real HTTP API (8 concurrent clients) *while* B's latency is measured, so creation and execution load overlap; the idle baseline is measured before and after A's activity and pooled, so slow drift of the shared machine's load does not bias the ratio. The ratio is reached because of the per-tenant run-creation pacing and parked steps (gap fix 7); without pacing, A's 429 retry storm alone produced 20–40× ratios on this machine. Machine load is printed with every run.
13. **Timer restart test** stops/starts the processes with SIGTERM (no `docker compose restart`); the timer is 2 minutes as in the spec.
14. **`FLUSHDB` test flushes Redis db 5**, the database assigned to this project (dev-stack keys are lost too and recover the same way).
15. **MCP risk metadata** (list tools take `cursor`, see gap fixes 3–5 for untrusted markers and ordering): `annotations['x-risk']` is sent, but MCP SDK clients drop unknown annotation keys, so the risk is also in `_meta['x-risk']` and in the description. Write tools implement `dryRun` partly in the API (`?dryRun=1` for tasks, notes, drafts, email send, invoice send/void) and partly in the server (`update_deal` diff).
16. **Idempotency**: HTTP `Idempotency-Key` is recorded in `effect_log` (`origin = 'api'`) and its response cached in `idempotency_records`; besides the spec's endpoints it is also honoured on task, note, draft, deal update/move and invoice void (used by MCP). Contract: ADR 0012. SMTP delivery is at-least-once (Message-ID = email id), see ADR 0004.
17. **Schema additions**: `step_runs` (`node_type`, `max_attempts`, `outcome`, `attempts` history, `pending_since`, `wait_key`), `workflow_runs` (`trigger_type`, `lock_version`, `test_definition`, `number`, `step_count`), `workflows` (trigger columns, webhook secret, `next_fire_at`, `last_scan_at`, `run_counter`, `template_key`), `version` on companies/contacts/deals, `tenant_id` on stages/lines/payments/versions/drafts, and tables `sessions`, `email_templates`, `email_messages` (mail outbox and drafts), `secrets` (AES-256-GCM), `import_jobs`, `idempotency_records`.
18. **Members**: inviting creates the account with a one-time temporary password (no invitation email).
19. **Feature flags**: `@ashamrai/flags-node` (API/engine: `workflow-ai-step`) and `@ashamrai/flags-react`/`flags-web` (SPA) are wired with built-in defaults; the project 02 relay was not running during verification, so only the fallback path was exercised.
20. **Realtime**: channels are `room:t.<tenantId>.…` with a tenant ACL; the SSE fallback for notifications and the polling fallback for the board exist but were only exercised manually by the frontend build agent, not by automated tests.
21. **Frontend**: the gaps reported by the first frontend build (keyboard moves limited to visible columns, dark mode without a toggle, run retry/cancel not exercised in a browser) are fixed and covered by Playwright (gap fix 8).
22. **Backend fixes after frontend review**: template preview with unresolved variables now returns 422 instead of 500; the pipeline funnel now uses "furthest stage reached" so `reached` is monotone and conversion ≤ 100 %; CSV import validates numbers through the zod schema. A reported "unreachable end node" in blank workflows could not be reproduced on the API (`$trigger → end` is present).
23. **Expression test count**: 582 table cases instead of ~300.
24. **Seed**: contains a prompt-injection string in an external note on purpose (for project 06's untrusted-field handling).

## Known gaps

- Throughput is bounded by Postgres round trips (11.6 statements per step). Next steps: a stored procedure for "complete step and advance run", batched completions, partitioning `step_runs` by month.
- `wait_for_event` also checks the outbox for matching events emitted after the run started, but not older ones.
- Tenant isolation is enforced in the application; RLS would be a second line of defence for future raw SQL.
- Only run creation is rate-limited per tenant; other API calls are not limited per tenant or token. The email rate limit (per tenant per minute) delays dispatch instead of failing.
- The API's `effect_log` row is written right after the domain transaction commits, not inside it (ADR 0012): a crash in that window lets a retry with the same key run the operation again.
- Authentication lookups are cached for 5 s per process; revoking a token or a membership takes up to 5 s to reach other API processes.
- The `ai_step` operator endpoint contract (`POST OPERATOR_URL`) is defined here; project 06 does not implement it yet (Wave 2), so it was verified against a local stub server only.
- MinIO objects created by tests are only removed by `make clean-test-objects`.

## Post-review fix (coordinator verification, 2026-10-05)

- **Kanban keyboard moves could land in the wrong column (real UI bug, flaky e2e ~1 in 5).** Each ArrowRight/ArrowLeft computed the next column from dnd-kit's `over`, which updates only after a re-render; fast key presses (or a busy machine) reused the stale column, so the card moved fewer columns than pressed. The keyboard coordinate getter now chains from the previous keyboard target (`nextKeyboardColumn`), falling back to `over` only for the first press. Regression unit test in `apps/web/test/theme-operator.test.tsx`; the e2e scenario passed 10/10 with `--repeat-each 10` after the fix.
